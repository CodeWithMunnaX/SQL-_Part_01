01 · Why databases exist

The Night the Spreadsheet Broke

Zwiggy stores everything in one file: orders_master.xlsx. Each row holds a full order — customer, phone, restaurant, restaurant's phone, dish, price. It is 80,000 rows now. Last Tuesday, one restaurant changed its phone number. Chaos followed.

Analogy first. Imagine writing your home address on every page of every notebook you own. Then you move house. You must fix thousands of pages, and you will miss some. Storing the same fact many times is a promise to eventually contradict yourself.

Three ways one big sheet breaks

Update anomaly

One real change = thousands of cell edits. Miss a few, and the sheet holds two "truths".

Insert anomaly

Can't add a new restaurant until it has an order. The row demands order details that don't exist yet.

Delete anomaly

Delete a restaurant's only order and the restaurant itself vanishes from your data.

⚡ Break the spreadsheet yourself

Spice Villa changes its phone number. Press the button in one big sheet mode and watch the edit sweep the phone column — and miss a row. Then switch to linked tables and do the same change. Count the cells each way. Try the delete too.

one big sheet: Spice Villa's phone is copied on 4 of 10 visible rows. (imagine 8,452 of 80,000 in the real file) → press a button above

Where this shows up in ML

Models trust data blindly. If one restaurant is spelled three ways, a demand model sees three weak restaurants instead of one strong one. Most "model bugs" in industry are storage bugs like this, inherited by the training set.

Key insight. Store every fact exactly once. Everything else tonight — tables, keys, schema — is the machinery that makes "once" possible.

02 · The warehouse and its guard

The Database and the Librarian (DBMS)

A database is an organised collection of data. A DBMS (database management system — MySQL, PostgreSQL, SQLite) is the software that guards it. You never touch the files. You hand the DBMS a request written in SQL, and it brings back a result table.

Analogy first. A library, and a librarian. You don't wander the shelves rearranging books. You hand over a request slip — "every book by this author, newest first" — and wait at the desk. The librarian knows the catalogue, fetches fast, and stops two people from rewriting the same book at once. Your SQL query is that slip.

SQL is declarative: you say what you want, never how to fetch it. The DBMS plans the how. Compare that with Pandas, where you run each step yourself, in order.

⚡ The round trip: follow your request

Press step to walk one request through the system. Then flip to do-it-yourself mode — the spreadsheet way — and see what changes. Watch who does the searching in each mode.

stage 1/5: you have a question: "top rated restaurants in Pune?"

Where this shows up in ML

Nearly every training dataset began life as a SQL query someone ran against a company database. Analysts spend more hours in SQL than in model code. It is the first screen in most data interviews.

Pitfall. "Database" and "DBMS" are not synonyms. The database is the organised data; the DBMS is the guard software. Saying "MySQL is a database" is like saying "the librarian is the library". Interviewers love this one.
Check yourself: Zwiggy's app and your Pandas notebook both need order data. Who is the only one allowed to read the data files directly?
The DBMS. Every reader — app, notebook, dashboard — goes through it with a query. That single doorway is what keeps the data consistent.

03 · The building block

Anatomy of a Table: Rows, Columns, Cells

Everything in a relational database lives in a table: a named grid. A column is one kind of fact, with a name and a type. A row is one complete record. A cell is one single fact, where a row meets a column.

You already know this shape. A table is a DataFrame that grew up. Same grid you used for eight weeks — plus rules. Columns are typed (a numeric price column refuses the text "free"). Every row has the same columns. And rows have no built-in order — there is no "row 7", only "the row whose id is 103".

The one question professionals ask first: the grain

The grain is what one row means. In orders, one row = one order. In order_items, one row = one dish inside one order. Misread the grain and every count you make afterwards is wrong.

⚡ Hover the grid, then beat the quiz

CELL = one fact: Priya ROW 3 = one complete record: [103, Priya, Paneer Pizza, 420] COLUMN "customer" = same kind of fact for every row - name (TEXT)

Where this shows up in ML

A feature matrix is a table whose grain you chose: one row per customer, per order, or per day. Choosing the grain is the first act of feature engineering. Feature stores are databases of exactly such tables.

Pitfall. Spreadsheet veterans say "the third row". Databases promise no row order at all — a table is a bag of rows until you sort it in a query. Name rows by key, never by position.

04 · The unique label

Primary Keys: Every Row Gets an Aadhaar

An angry call arrives: "Where is my biryani?" — from Munna Kumar. Zwiggy has two of those. Which one is starving? Without a guaranteed-unique label per row, you cannot say. That label is the primary key (PK).

DEFINITION: PRIMARY KEY (PK)

A Primary Key (PK) is a column (or set of columns) in a table that uniquely identifies each row. It must be unique, never NULL, and stable over time.

Example: Primary Key in Customers Table

Here, customer_id is the Primary Key. Even if we have two customers named "Munna Kumar", they have different primary keys (2 and 4), making each record uniquely identifiable.

customer_id (PK ★) name city phone
1 Ananya Iyer Bengaluru 98450-11111
2 Munna Kumar Pune 98200-22222
3 Priya Patel Mumbai 98200-33333
4 Munna Kumar Pune 98550-44444
Analogy first. India met this exact problem at national scale. Names repeat, addresses change, phone numbers get recycled — so Aadhaar gives each person one permanent, meaningless, unique number. Your college does it with roll numbers. A primary key is a roll number for rows.

The three-question audit

A column being auditioned is a candidate key. Ask three questions. Is it unique for every row, forever? Is it always present — never blank? Is it stable — never edited later? One "no" and the candidate is out.

⚡ Audit the candidates yourself

Pick a candidate column. Duplicates turn red, blanks turn amber, and the console delivers the verdict. Then press +3 signups to grow the table and watch which candidates crack under growth.

candidate:
auditing candidate: customer_id unique for every row? yes always present? yes stable over time? yes (system-assigned, never edited) VERDICT: passes all three - fit to be PRIMARY KEY.

A key built from real-world data (email, phone) is a natural key. A made-up id assigned by the system is a surrogate key. Real systems choose surrogates, because the audit above keeps ending the same way: the real world changes; meaningless labels don't.

Where this shows up in ML

You met broken keys in Part 2: merging DataFrames on a column with duplicates silently multiplied rows. Duplicated rows then leak between train and test splits — and your accuracy becomes a lie. Clean keys guard honest models.

Pitfall. Never use phone or email as a primary key. Families share phones, telecoms recycle numbers, people change emails, and some fields arrive blank. And never edit a key's value later — every pointer to it would dangle.

Bridge → Unique labels at home. Now: how does another table point at them?

05 · Tables hold hands

Foreign Keys: Pointers with a Bodyguard

Customers live in customers, orders in orders. But an order belongs to a customer. So each order stores one small thing: the customer's primary key. A column holding another table's PK values is a foreign key (FK).

DEFINITION: FOREIGN KEY (FK)

A Foreign Key (FK) is a column in a table that links to the Primary Key (PK) of another table. It acts as a cross-reference or pointer to establish a relationship.

Example: Foreign Key linking Orders to Customers

Here, customer_id in the orders table is a Foreign Key (FK) that points directly to the customer_id in the customers table.

customers (Parent Table)
customer_id (PK ★) name
1 Ananya Iyer
2 Munna Kumar
orders (Child Table)
order_id customer_id (FK →) amount
101 2 540
102 1 260
Analogy first. A cloakroom token. The token is tiny, but it points at exactly one bag on one hook. And there's an attendant. Nobody gets a token for a hook that doesn't exist. No bag is discarded while someone holds its token. That attendant is called referential integrity.

Where this shows up in ML

Building "average order value per city" means walking orders → customers through this key. Next week's joins are foreign keys in action. Broken pointers surface in Pandas as mystery NaNs after a merge.

Pitfall. A foreign key may repeat — customer 2 on many orders is correct and normal. Uniqueness is the primary key's job, in its own table. PK = unique label at home. FK = repeatable pointer from elsewhere.
Check yourself: could Zwiggy store the customer's name and phone on every order row instead of a pointer? What goes wrong?
That's the Section 01 disaster again: the same fact stored thousands of times. When the customer changes their phone, you edit every order they ever placed — and miss some. Store the fact once; point at it everywhere else.

Bridge → Pointers connect two tables. But how many of these go with how many of those? Three shapes cover every case.

06 · The three shapes

Relationship Shapes: 1:1, 1:N, N:M

Every pair of tables has a shape, and two questions find it. Can one A have many B? Can one B have many A? No–no means 1:1. Yes–no means 1:N. Yes–yes means N:M — and N:M needs a trick.

The trick for N:M. One order holds many dishes; one dish appears in many orders. Neither table can store the pointer — a cell can't hold "dishes 7, 12, 31". So a third table steps in: a junction table. order_items has one row per (order, dish) pair, plus pair-level facts like quantity. Your CodeWithMunnaX enrolment works the same way: students, courses, and an enrolment register between them.

Where does the FK live? Always on the many side. One customer, many orders → orders carries customer_id. The "one" side stays clean.

⚡ The classifier game — 6 rounds

Read the pair, ask the two questions in your head, then answer. The canvas draws the true shape after each round. Play to 6/6 — in class, shout your answer before clicking.

Where this shows up in ML

Shapes predict row counts after joins. Join orders→customers (many-to-one): row count unchanged. Join orders→order_items (one-to-many): rows multiply. Analysts who forget this double-count revenue. You saw the same effect in Pandas merges.

Pitfall. Never model N:M by stuffing a list into one cell ("7,12,31") or adding dish_1, dish_2, dish_3 columns. Both designs cap growth and make counting nearly impossible. Two yes answers = junction table, every time.

07 · The blueprint

Design Zwiggy's Schema, Step by Step

A schema is the blueprint: which tables exist, their columns and types, their keys, and the links between them. Architects draw before laying bricks. Analysts draw before loading data. Six moves, one recipe you can reuse on any business.

The six moves

1 · List the nouns the business talks about — each becomes a table.   2 · Say each table's grain out loud.   3 · Give every table a surrogate primary key.   4 · Attach each fact to the one table where it's true once.   5 · Classify every relationship; place FKs; junction for N:M.   6 · Hunt repetition — any fact that would repeat sits on the wrong table.

The repetition-hunting instinct has a formal rulebook called normalization (1NF, 2NF, 3NF) — it arrives on 27 July. Tonight you learned the instinct the rulebook formalises.

Where this shows up in ML

Every analytics warehouse is this pattern at scale — the "star schema" behind dashboards. Fact tables (orders) in the middle, descriptive tables (customers, restaurants) around them. Your feature pipelines will walk this shape, key by key.

Pitfall. No orders_delhi, orders_pune, orders_july tables. "Delhi" is data, so it lives inside a column. Splitting tables by data values is the second-most-common beginner bug, right after copying facts everywhere.
Check yourself: Zwiggy adds delivery partners. One partner delivers many orders; an order has one partner. What changes in the schema?
Add a partners table (partner_id ★, name, phone…) and one FK column orders.partner_id. Relationship is 1:N, so the pointer sits on the many side — orders. No other table changes.

📖 SQL Cheat Sheet

1. SELECT (Column Projection)

Choose columns to retrieve.

SELECT name, city FROM customers;
SELECT * FROM orders; -- All columns

2. WHERE (Row Filtering)

Filter rows matching condition.

SELECT * FROM restaurants WHERE city = 'Pune';
SELECT * FROM orders WHERE amount > 500;

3. JOIN (Merge Tables)

Join matching rows by PK/FK keys.

SELECT orders.order_id, customers.name FROM orders JOIN customers ON orders.customer_id = customers.customer_id;

4. Key Relational Terms

  • PK (Primary Key): Unique ID for every row in a table.
  • FK (Foreign Key): ID pointing to another table's PK.
  • Schema: The blueprint of tables, columns, and relationships.
  • Grain: What one single row represents.
